# DBスキーマ管理方針

## 適用範囲と方針

## Go モジュールと配置

バックエンドは単一 Go モジュール `cellar-app`（`go.mod` の Go バージョン指定は 1.25.0）です。主な DB 関連パッケージは `model/`（永続化モデル）、`dto/`（API 契約・変換）、`database/`（接続・AutoMigrate）、`repository/`（GORM データアクセス）です。機能追加時は既存の責務分割を維持してください。

### 今後の方針

1. DB テーブルの構造を表す Go の GORM 永続化モデルをスキーマ定義の正とします。
2. DB スキーマの追加・安全な拡張には GORM `AutoMigrate` を使用します。
3. Atlas、Goose など別のマイグレーションツールは導入しません。
4. DB 永続化モデルと API のリクエスト・レスポンス DTO を分離します。
5. `AutoMigrate` 対象は `database.Migrate` 内でモデル型を明示列挙し、DTO・集計用構造体・リクエスト専用構造体を渡しません。
6. 既存データと他システムの利用を保護し、破壊的変更は `AutoMigrate` 任せにしません。

### 現在の実装

- 永続化モデルは `model/model.go`、DTO は `dto/dto.go`、相互変換は `dto/model_conversion.go` にあります。
- `database.Migrate` は次の11型を明示列挙して `db.AutoMigrate` を呼びます。

```go
&model.Country{}
&model.WineType{}
&model.DesignationType{}
&model.Region{}
&model.Appellation{}
&model.Grape{}
&model.Wine{}
&model.Bottle{}
&model.WineGrape{}
&model.InventoryDailySnapshot{}
&model.InventoryDailySnapshotDetail{}
```

- DTO は列挙されていません。`dto.Stats` 等の集計結果構造体も DB テーブルではありません。
- `main.go` は PostgreSQL 接続の直後、LLM 初期化と HTTP サーバー起動より前に `database.Migrate(db)` を実行します。エラー時はプロセスを終了します。
- モデルには既存テーブル・制約名に合わせた明示的な型、カラム名、外部キー名、削除動作のタグがあります。既存 DB との互換性を保つ理由がある場合、制約名や `TableName` を不用意に変更しません。
- 永続化モデルのテーブル名・主キー、複数カラムの型・NULL性、複数 FK 名と削除動作を確認する Go テストがあります。ただし実 PostgreSQL に対して DDL や実スキーマの一致を検証するテストではありません。

### 方針と現状の差

モデルの正本化、DTO 分離、AutoMigrate 対象の明示列挙は現行コードで実施されています。一方、運用上の安全策はコードに組み込まれていません。

- `main.go` は毎回の API 起動時に AutoMigrate を自動実行します。バックアップ確認、承認、環境選択、破壊的変更の検知を挟む仕組みはありません。
- テストはモデル解析・変換を検査しますが、PostgreSQL 上での migration／既存データ保護／復元は検査しません。
- バックアップ後にのみ本番起動するという保証や、定期バックアップ・復元訓練の自動化は確認できません。

したがって、今後は起動時 migration の前に手順上のバックアップ・隔離 DB 検証を必須とし、運用可能な自動化がない環境では手動チェックリストと作業記録で補ってください。

## DBモデルとDTOの責務

| 種別 | 配置 | 責務 | `AutoMigrate` |
|---|---|---|---|
| 永続化モデル | `model/` | DB のテーブル・カラム・関連・制約を表す | DB テーブルにする型のみ列挙 |
| API DTO／リクエスト | `dto/` | JSON 契約、入出力形状、必要な関連名や集計値を表す | 登録しない |
| 集計・サービス内構造体 | `dto/`、`service/` 等 | API 集計結果や計算中の値を表す | テーブルでない限り登録しない |

フィールド追加時は保存が必要かを判断し、DB 列が必要ならモデル、API で公開するなら DTO と変換処理を別々に更新します。API フィールドの追加だけで DB 列が必要とは限りません。逆も同様です。

## 命名と GORM タグ

- Go 構造体名は単数 PascalCase、フィールド名は PascalCase とし、GORM の標準命名による複数形テーブル名・`snake_case` カラム名を基本とします。
- 既存テーブル名・カラム名を維持する必要がある場合は `TableName()` または `column:` タグを使います。現在 `WineGrape.TableName()` は `wine_grapes` を明示します。
- GORM タグの `type`、`size`、`not null`、`primaryKey`、`uniqueIndex`、`index`、`check`、`default`、`constraint`、`OnDelete` はモデルの宣言意図を示します。タグだけで稼働 DB が同じ定義であることを証明するものではありません。
- nullable を扱う DB フィールドは、原則として Go の pointer など null とゼロ値を区別できる表現を使います。非 pointer 型でも `not null` タグのないフィールドがあるため、Go ゼロ値を理由に DB の NULL 可否を推測しません。
- 制約・インデックス名は明示名や既存テストを確認します。名前変更は DB 上で新旧が重複作成される、または旧制約が残る可能性を考慮して事前調査します。

## 新しいテーブルを追加する手順

1. テーブルが実際に永続化対象か確認し、データ所有者、寿命、削除規則、NULL の意味、キー、検索要件を決めます。
2. `model/` に永続化モデルを追加し、カラム型・必須性・既定値・制約・関連をタグで明示します。既存 DB オブジェクトとの名前衝突も確認します。
3. `database/migrate.go` の `Migrate` にモデルを明示的に追加します。DTO や統計用構造体は追加しません。
4. API から扱う必要がある場合のみ `dto/` と変換・handler/service/repository を更新します。永続化モデルそのものを API 契約として流用しません。
5. model schema テストにテーブル名・主キー・重要な型・NULL・制約の検証を追加します。必要な削除・関連動作はテストで確認します。
6. 空 DB と既存データのある隔離 PostgreSQL の両方で起動時 AutoMigrate を検証し、行数・既存制約・実行後定義を比較します。
7. バックアップを取得・復元確認した後、承認された環境に適用します。手順は[DB運用手順](./database-operations.md)を参照します。

## 既存テーブルへの追加・変更

### 比較的安全な追加

新しい nullable 列、または既存行に適用できる安定した default を伴う列の追加は `AutoMigrate` の対象になり得ます。それでも、テーブル規模、ロック、default の挙動、アプリ旧版との互換性を検証し、事前バックアップと隔離 DB テストを行ってください。

必須列を既存データに追加する場合は、いきなり `NOT NULL` にせず、nullable 追加 → 既存行のバックフィル → 値検査 → 制約追加という段階的移行を基本とします。段階ごとにアプリケーションの読み書きとの互換性を確認します。

### 個別対応が必要な変更

| 変更 | 注意点と推奨対応 |
|---|---|
| カラム削除 | `AutoMigrate` が既存カラムを安全に削除するものとして扱わない。コード・API・他サービス・手動 SQL・バックアップ利用者を調査し、保持期間を経た明示的な削除計画を作る |
| カラム名変更 | 新カラム追加、データコピー／二重書き、読み取り切替、検証、旧カラム削除の段階移行を検討する。単に Go フィールド名を変えると意図しない新列を作る恐れがあるため、明示 `column:` と実 DB を確認する |
| 型変更 | 既存値の変換可能性、桁あふれ・精度・時刻・NULL・インデックス・FK を調査する。必要なら新列と変換 SQL を使う。隔離コピーで件数と値を比較する |
| `NOT NULL` 追加 | NULL 件数を確認し、意味が正しい値で補完してから制約を追加する。0／空文字での一括置換を自明な正解としない |
| ユニーク制約追加 | 重複値を事前検査・解消する。NULL の一意性や複合キーの意味、既存書き込みとの競合を確認する |
| インデックス変更 | DB サイズ、ロック、書き込み影響、既存インデックス名・重複を調査する。作成・削除を `AutoMigrate` だけに任せず、対象環境の PostgreSQL で個別計画を検証する |
| 既存データ変換 | 変換規則、対象件数、再実行時の安全性、ロールバック方法を明記し、バックアップと隔離 DB の前後比較を必須にする |

SQL が必要な場合は、ツール導入方針を変えず、レビュー可能な手動実行手順または一時的な運用 SQL として管理し、実行対象・前提・検証・完了記録を残します。恒久的に Goose / Atlas 等へ移行することを意味しません。

## 不整合・直接変更の扱い

- モデルと実 DB が異なる場合、差異を直ちに `AutoMigrate` で上書きしません。環境名、実カラム・型・NULL・default・制約・索引、データ件数、管理外利用を記録します。
- DB を直接変更した場合は、変更者、日時、対象 DB、SQL／操作、理由、前後の定義、データ検証、復旧用バックアップを記録します。必要な変更はモデルとテストへ反映し、以後の AutoMigrate と整合させます。
- モデルにないテーブル・列・制約を、アプリケーションの grep で使われていないことだけを根拠に削除しません。別サービスや運用作業の依存を確認します。
- 変更レビューでは、データ損失、既存行への適用、FK 削除動作、長時間ロック、API互換性、旧・新バイナリの共存、バックアップ復旧手段を確認します。

## テスト方針

- PR 前に `go test ./...` を実行します。既存 model テストは GORM のモデル解析に基づくテストであり、実 DB マイグレーションテストではありません。
- スキーマに影響する変更は PostgreSQL の使い捨て環境に既存 DB の匿名化または安全なコピーを復元し、実 AutoMigrate を試します。DDL・制約・インデックス・件数・代表値・削除動作を前後比較します。
- 本番適用前に復元テストを完了し、適用中に起動するアプリケーションの挙動と監視方法を定めます。
